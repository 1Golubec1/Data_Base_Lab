# Лабораторная работа 8 (дополнительная)

## Тема

Транзакции и уровни изоляции в PostgreSQL.

В наборе файлов приведены отдельные SQL-сценарии для демонстрации:

- `non-repeatable read`;
- `phantom read`;
- `write skew` на уровне `REPEATABLE READ`;
- проверки `write skew` на уровне `SERIALIZABLE`;
- использования `SAVEPOINT` и `ROLLBACK TO SAVEPOINT`.

Сценарии рассчитаны на запуск в `pgAdmin4` через `Query Tool`.

## Общий принцип запуска

Для сценариев конкурентного доступа нужно открыть две независимые вкладки `Query Tool` в pgAdmin4. Первая вкладка считается `Сессией 1`, вторая вкладка считается `Сессией 2`.

Важно: нельзя запускать все файлы подряд в одной вкладке. В этом случае не будет двух параллельных транзакций, и аномалии конкурентного доступа не воспроизведутся.

Команды нужно выполнять строго по номерам файлов. Файлы с именем `session_1` выполняются в первой вкладке, файлы с именем `session_2` выполняются во второй вкладке.

## Подготовка тестовых данных

Перед началом работы выполните файл:

```text
00_prepare_test_data.sql
```

Его можно выполнить в любой одной вкладке `Query Tool`. Скрипт удаляет старые тестовые строки с id `800001...800005` и заново создаёт фиксированный набор строк в таблице `taxi_order`.

После выполнения должны быть созданы строки:

```text
800001 | waiting  | 100.0000 | NULL
800002 | waiting  | 150.0000 | NULL
800003 | accepted | 200.0000 | 5
800004 | accepted | 220.0000 | 6
```

Строка `800005` специально не создаётся в подготовительном скрипте. Она используется в сценарии `phantom read` как новая фантомная строка.

## 1. Non-repeatable read

Папка:

```text
01_non_repeatable_read
```

Назначение сценария: показать, что на уровне `READ COMMITTED` повторное чтение одной и той же строки внутри одной транзакции может дать другой результат, если между чтениями другая транзакция изменила строку и выполнила `COMMIT`.

Порядок запуска:

```text
1. В любой вкладке выполнить 00_reset.sql.
2. В Сессии 1 выполнить 01_session_1_first_read.sql.
3. В Сессии 2 выполнить 02_session_2_update_commit.sql.
4. В Сессии 1 выполнить 03_session_1_second_read_commit.sql.
```

Ожидаемый результат:

```text
Первое чтение в Сессии 1:  current_cost = 100.0000
Вторая сессия меняет цену: current_cost = 999.0000
Второе чтение в Сессии 1: current_cost = 999.0000
```

Вывод: одна и та же транзакция в Сессии 1 дважды прочитала одну и ту же строку, но получила разные значения. Это и есть `non-repeatable read`.

## 2. Phantom read

Папка:

```text
02_phantom_read
```

Назначение сценария: показать, что на уровне `READ COMMITTED` повторное выполнение одного и того же запроса по условию может увидеть новую строку, вставленную и зафиксированную другой транзакцией.

Порядок запуска:

```text
1. В любой вкладке выполнить 00_reset.sql.
2. В Сессии 1 выполнить 01_session_1_first_count.sql.
3. В Сессии 2 выполнить 02_session_2_insert_commit.sql.
4. В Сессии 1 выполнить 03_session_1_second_count_commit.sql.
```

Ожидаемый результат:

```text
Первый COUNT в Сессии 1:  waiting_orders = 2
Сессия 2 вставляет новый заказ 800005 со статусом waiting.
Второй COUNT в Сессии 1: waiting_orders = 3
```

Вывод: во втором чтении появилась новая строка, подходящая под условие `status = 'waiting'`. Это и есть `phantom read`.

## 3. Write skew на REPEATABLE READ

Папка:

```text
03_write_skew_repeatable_read
```

Назначение сценария: показать аномалию `write skew`, когда две транзакции читают один и тот же набор данных, проверяют общий бизнес-инвариант, но изменяют разные строки. Прямого конфликта записи нет, поэтому обе транзакции могут завершиться успешно, хотя итоговое состояние нарушает инвариант.

Используемый инвариант:

```text
Среди заказов 800003 и 800004 должен остаться хотя бы один активный заказ со статусом accepted или way.
```

Порядок запуска:

```text
1. В любой вкладке выполнить 00_reset.sql.
2. В Сессии 1 выполнить 01_session_1_check_invariant.sql.
3. В Сессии 2 выполнить 02_session_2_check_invariant.sql.
4. В Сессии 1 выполнить 03_session_1_cancel_one_order_commit.sql.
5. В Сессии 2 выполнить 04_session_2_cancel_second_order_commit.sql.
6. В любой вкладке выполнить 05_check_result.sql.
```

Ожидаемый результат:

```text
Сессия 1 видит active_orders = 2.
Сессия 2 видит active_orders = 2.
Сессия 1 отменяет заказ 800003.
Сессия 2 отменяет заказ 800004.
Итоговый active_orders = 0.
```

Вывод: обе транзакции приняли решение на основе старого снимка данных и изменили разные строки. В результате бизнес-инвариант оказался нарушен. Это и есть `write skew`.

## 4. Write skew на SERIALIZABLE

Папка:

```text
04_write_skew_serializable
```

Назначение сценария: показать, что уровень `SERIALIZABLE` должен предотвращать такое некорректное состояние. Одна из транзакций может завершиться ошибкой сериализации.

Порядок запуска:

```text
1. В любой вкладке выполнить 00_reset.sql.
2. В Сессии 1 выполнить 01_session_1_check_invariant.sql.
3. В Сессии 2 выполнить 02_session_2_check_invariant.sql.
4. В Сессии 1 выполнить 03_session_1_cancel_one_order_commit.sql.
5. В Сессии 2 выполнить 04_session_2_cancel_second_order_commit.sql.
```

Ожидаемый результат: при выполнении `COMMIT` во второй сессии возможна ошибка вида:

```text
ERROR: could not serialize access due to read/write dependencies among transactions
```

Это нормальный результат для данного сценария. Он означает, что PostgreSQL обнаружил конфликт сериализации и не позволил зафиксировать состояние, которое не соответствует последовательному выполнению транзакций.

После такой ошибки во второй сессии нужно выполнить:

```text
05_after_serialization_error.sql
```

Файл делает `ROLLBACK` и показывает итоговое состояние строк `800003` и `800004`.

## 5. SAVEPOINT и ROLLBACK TO SAVEPOINT

Папка:

```text
05_savepoint_rollback_to
```

Этот сценарий не требует двух сессий. Его нужно выполнить в одной вкладке `Query Tool`:

```text
01_run_in_one_session.sql
```

Ожидаемый ход выполнения:

```text
1. Заказ 800001 имеет status = waiting, current_cost = 100.0000.
2. Создаётся SAVEPOINT before_status_change.
3. Статус временно меняется на cancelled.
4. Выполняется ROLLBACK TO SAVEPOINT before_status_change.
5. Статус возвращается к waiting.
6. Затем current_cost меняется на 180.0000.
7. Выполняется COMMIT.
```

Ожидаемое итоговое состояние:

```text
800001 | waiting | 180.0000
```

Вывод: `ROLLBACK TO SAVEPOINT` отменяет только изменения после указанной точки сохранения, но не завершает всю транзакцию. После частичного отката транзакция может продолжить выполнение и затем успешно зафиксироваться через `COMMIT`.

## Частые ошибки при запуске

Если результат не совпадает с ожидаемым, проверьте следующее.

Первая частая ошибка — запуск всех файлов в одной вкладке. Тогда не возникает параллельных транзакций, и лабораторная теряет смысл.

Вторая частая ошибка — забытый `COMMIT` или `ROLLBACK` в одной из вкладок. Если транзакция осталась открытой после ошибки, выполните `ROLLBACK;`.

Третья частая ошибка — повторный запуск `phantom read` без очистки строки `800005`. Для этого перед экспериментом нужно выполнять `02_phantom_read/00_reset.sql`.

Четвёртая частая ошибка — выполнение файлов не по номерам. В этой лабораторной порядок важен, потому что результат зависит от чередования действий двух сессий.
